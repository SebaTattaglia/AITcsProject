Deployment and Rollback Runbook

This runbook covers how services are released to production through the CI/CD pipeline and how to roll back a bad release.

Pipeline stages

  1. Build: Docker image tagged with the Git commit SHA. Images tagged latest are rejected.
  2. Test: lint, type check, unit and integration tests, dependency vulnerability scan.
  3. Staging: automatic deploy and smoke tests against staging.
  4. Production: canary release to 10% of pods for 15 minutes, then 100% if error rate and p95 latency stay within the SLO.

Deployment windows

Production deploys are allowed Monday to Thursday, 09:00 to 16:00 local time. Friday and weekend deploys need approval from the on-call lead. Changes freeze during the last 3 business days of each quarter.

Database migrations

Migrations run as a separate job before the new pods start and must be backwards compatible with the previous release (expand and contract pattern): add the new column first, deploy code that writes both, backfill, and remove the old column in a later release.

Rollback procedure

Roll back as soon as the canary breaches the SLO, without waiting to find the root cause.

kubectl rollout history deployment/orders-api -n orders
kubectl rollout undo deployment/orders-api -n orders --to-revision=41
kubectl rollout status deployment/orders-api -n orders --timeout=5m

If the release included a migration, do not roll back the database; the expand and contract pattern guarantees the previous version still works with the new schema.

After the rollback

  • Announce it in the #deployments channel with the ticket id.
  • Open an incident ticket and attach the dashboard links and the correlation ids of failing requests.
  • Write a blameless post-mortem within 5 business days for any customer-facing impact.
